# 协作平台 API 错误排查手册

## 1. 调用固定 API 报错时，标准错误响应结构与排查顺序是什么？

当你调用协作平台固定接口（`GET /sandbox/product/v1/me`、`GET /sandbox/product/v1/projects`、`GET /sandbox/product/v1/projects/{id}`）失败时，服务端会返回非 `200` 的 HTTP 状态码及标准错误 JSON 结构：

```json
{
  "status": "error",
  "request_id": "req_20261016_089",
  "environment": "sandbox",
  "error": {
    "http_status": 403,
    "code": "PROJECT_ACCESS_DENIED",
    "message": "Current user does not have access to project proj_core_01.",
    "details": {
      "project_id": "proj_core_01",
      "required_scope": "project:read",
      "credential_has_scope": true,
      "user_has_project_access": false
    }
  }
}
```

请勿仅凭经验猜测“可能是 Token 坏了”或“多试几次就好了”。你可以前往左侧导航栏 **「开发者与 API 中心 > 调用记录与配额看板」** 自查调用详情，或将上述脱敏错误响应（`http_status`、`error.code`、`error.details`）复制到 **「帮助与支持 > Ordo 智能支持中心」** 由助手按以下规则为你分析原因：

| HTTP 状态码 | 业务错误标识（`error.code`） | 核心故障原因 | 对应页面自查与处理方向 |
| :--- | :--- | :--- | :--- |
| `400` | `INVALID_ARGUMENT` | 路径参数 `{id}` 格式非法、传入未定义查询参数或分页参数越界 | 对照接口规范修正 URL 路径与查询参数，在 **「沙箱调试台」** 页面验证 |
| `401` | `UNAUTHORIZED` | 请求头缺失、凭据不存在、凭据已过期/已吊销或租户会话失效 | 在 **「开发者与 API 中心 > 凭据管理」** 页面核对或重新生成有效凭据 |
| `403` | `INSUFFICIENT_SCOPE` | **仅缺少接口 `scope`**：调用用户有权访问项目，但凭据未勾选 `project:read` | 在 **「凭据管理」** 页面为该凭据补充勾选 `project:read` |
| `403` | `PROJECT_ACCESS_DENIED` | **仅缺少项目资源权限**：凭据已含 `project:read`，但调用用户无该项目访问权（或跨租户） | 同空间项目在 **「项目中心 > 申请访问项目」** 申请或由负责人添加权限；跨租户项目立即停止调用 |
| `403` | `SCOPE_AND_ACCESS_DENIED` | **同时缺少 `scope` 与项目权限**：凭据既无 `project:read`，调用用户也无该项目访问权 | **必须同时在「凭据管理」补齐 `project:read` 并在页面完成项目权限授权** |
| `429` | `RATE_LIMITED` | **短时限流**：单个 API 凭据在 60 秒固定窗口内请求超过 60 次 | 停止同凭据并发请求，等待 `retry_after_seconds` 秒且确认日配额充足后复测 |
| `429` | `QUOTA_EXCEEDED` | **累计额度耗尽**：所属工作空间当日累计调用已达 5,000 次上限 | 等待次日 `00:00（UTC+8）` 自动重置，或在 **「帮助与支持 > 我的工单」** 页面提交工单 |

## 2. 调用接口返回 HTTP 400（`INVALID_ARGUMENT`）如何排查？

- **现象**：请求返回 HTTP `400`，`error.code` 为 `INVALID_ARGUMENT`，请求在进入认证与权限检查前被拒绝。
- **可能原因**：
  1. 调用 `GET /sandbox/product/v1/projects/{id}` 时，路径参数 `{id}` 填写了项目中文名称（如 `核心改造项目`）、包含了大写字母或特殊字符，不符合 `^proj_[a-z0-9_]{3,27}$` 格式规范。
  2. 调用 `GET /sandbox/product/v1/projects` 时，`visibility` 传入了除 `workspace_public`、`private` 以外的字符串，或 `page_size` 超出了 `1`～`50` 的允许范围（如传入 `page_size=200`）。
  3. 调用 `GET /sandbox/product/v1/me` 或 `GET /sandbox/product/v1/projects/{id}` 时，URL 中附带了接口未定义的额外查询参数（如 `?debug=true`），或使用了 `POST`/`PUT` 等非 `GET` 方法。
- **检查方法**：
  - 查看接口返回的错误响应体 `error.details` 中指出的非法字段名（`field`）与原因说明；或将你请求的 URL 路径、查询参数与脱敏报错粘贴到 **Ordo 智能支持中心**，对照固定接口规范逐项核对（注：Ordo 仅依据规范分析你提供的参数，不直接执行请求校验工具）。
- **处理建议**：
  - 将路径参数 `{id}` 替换为准确的 `project_id`（可在 **「项目中心」** 对应项目的设置或分享弹窗中复制，确保以 `proj_` 开头且仅含小写字母、数字和下划线，长度 8～32 位）。
  - 删除所有未在接口文档中声明的查询参数，确保 `page_size` 在 `1`～`50` 之间，且 HTTP 方法固定为 `GET`。
- **验证结果**：修正参数后，在 **「开发者与 API 中心 > 沙箱调试台」** 页面或客户端使用原凭据重新发送请求并观察返回结果；确认请求不再返回 `400`（若后续环节存在凭据、权限或配额问题，再按对应状态码继续排查）。

## 3. 调用接口返回 HTTP 401（`UNAUTHORIZED`）如何排查？

- **现象**：调用任意固定产品接口（包括 `GET /sandbox/product/v1/me`）均直接返回 HTTP `401`，`error.code` 为 `UNAUTHORIZED`。
- **可能原因**：
  1. 请求头未携带 `Authorization: Bearer <YOUR_CREDENTIAL_TOKEN>`，或令牌字符串在复制时首尾截断、混入多余空格。
  2. 该 API 凭据已超过设定的有效期（Expired），或已在 **「凭据管理」** 页面被手动吊销（Revoked）。
  3. 凭据所绑定的调用用户已被工作空间管理员（`admin`）移出当前工作空间。
- **检查方法**：
  1. 前往左侧导航栏 **「开发者与 API 中心 > 凭据管理」** 页面，按脱敏凭据标识查找该凭据：
     - 若状态显示为 **「已过期」** 或 **「已吊销」**，则确认为凭据本身失效。
  2. 在 **「开发者与 API 中心 > 沙箱调试台」** 页面选用该凭据对应的 `test_credential_id` 调用 `GET /sandbox/product/v1/me`：
     - 若页面沙箱测试正常返回 `200 OK`，而你本地脚本仍报 `401`，说明本地脚本配置文件中的明文 Token 填写错误或未加载最新环境变量。
- **处理建议**：
  - 若凭据已过期或已吊销，在 **「凭据管理」** 页面点击 **「+ 创建 API 凭据」** 生成新凭据，并在客户端代码中更新 `Authorization` 请求头。
  - 若仅是本地配置拼写有误，核对并修复 `Bearer <YOUR_CREDENTIAL_TOKEN>` 格式（注意 `Bearer` 后必须有一个半角空格）。
- **验证结果**：在 **「沙箱调试台」** 或客户端先调用 `GET /sandbox/product/v1/me`，观察是否返回 `200 OK` 及正确的 `user_id`、`workspace_id`，确认认证通过后再继续调用项目接口。

## 4. 为什么返回 HTTP 403？如何严格区分三种 403 权限拒绝场景？

收到 HTTP `403` 说明你的 API 凭据已通过 `401` 身份认证，但未能通过第 3 步的**“接口 `scope` + 调用用户项目访问权”双重校验**。请查看响应体中的 `error.code` 与 `error.details`（或将脱敏响应粘贴给 Ordo 协助分析），严格区分以下三种场景，切勿盲目更换凭据：

### 4.1 场景一：仅缺少接口 `scope`（`INSUFFICIENT_SCOPE`）

- **现象**：
  - 调用用户在协作平台网页端可以正常打开并查看目标项目（例如调用用户是本空间 `admin`，或是有权访问公开项目的 `member`，或是已获授权的协作者），且调用 `GET /sandbox/product/v1/me` 返回 `200 OK`。
  - 但调用 `GET /sandbox/product/v1/projects` 或 `GET /sandbox/product/v1/projects/{id}` 时返回 HTTP `403`，`error.code` 为 `INSUFFICIENT_SCOPE`（`credential_has_scope: false`，`user_has_project_access: true`）。
- **可能原因**：当前使用的 API 凭据在创建或编辑时，只勾选了默认的 `profile:read`，**未勾选 `project:read` 权限范围**。注意：**即使是工作空间管理员（`admin`），调用项目接口也必须满足凭据包含 `project:read` 的条件，不能跳过 `scope` 校验。**
- **检查方法**：
  - 前往左侧导航栏 **「开发者与 API 中心 > 凭据管理」** 页面，查看该凭据的 **「权限范围（Scope）」** 列是否缺少 `project:read` 标签；同时查看响应报文 `error.details.credential_has_scope` 是否为 `false`。
- **处理建议**：
  - 无需去申请项目访问权。
  - 直接在 **「开发者与 API 中心 > 凭据管理」** 页面点击该凭据右侧的 **「编辑权限范围」**，勾选 **`project:read`** 并点击 **「保存」**。
- **验证结果**：保存后，继续使用**原调用用户身份及该凭据**在 **「沙箱调试台」** 页面或客户端重新请求目标接口并观察结果；若其他校验条件（如配额）均满足，接口将返回 `200 OK`。

### 4.2 场景二：仅缺少项目资源访问权（`PROJECT_ACCESS_DENIED`）

- **现象**：
  - 凭据已勾选 `project:read`，调用 `GET /sandbox/product/v1/projects` 可以正常返回 `200 OK`。
  - 但调用 `GET /sandbox/product/v1/projects/{id}` 访问某个具体项目时返回 HTTP `403`，`error.code` 为 `PROJECT_ACCESS_DENIED`（`credential_has_scope: true`，`user_has_project_access: false`）。
- **可能原因**：
  1. **正式成员（`member`）访问未授权的私有项目**：目标项目 `{id}` 为本工作空间的私有项目（`private`），而凭据绑定的 `member` 用户尚未被添加进该项目的协作者名单。
  2. **访客（`guest`）访问未明确授权的项目**：凭据绑定的调用用户角色为 `guest`，尚未获得该项目 `{id}` 的明确授权（`guest` 对未授权的公开项目和私有项目均会返回此错误）。
  3. **跨租户越权访问**：目标项目 `{id}` 归属于另一家企业租户（`tenant`）。任何角色（包括 `admin`）跨租户调用他方项目均会被直接拒绝。
- **检查方法**：
  - 使用调用用户账号在网页端 **「项目中心」** 搜索或尝试打开该项目 `{id}`：
    - 若页面提示“该项目属于当前工作空间，但你尚未获得访问权限”，则为本空间项目缺权。
    - 若页面提示“未找到该项目或不属于当前租户”，则为跨租户越权或项目 ID 错误。
- **处理建议**：
  - **属于本工作空间的未授权项目**：由调用用户在 **「项目中心 > 申请访问项目」** 页面填写该项目 `{id}` 提交 `read` 权限申请（状态为 `submitted`），等待**本工作空间管理员（`admin`，在「空间管理 > 权限审批中心」操作）或该项目负责人（`manage`，在该项目「项目成员与权限 > 待审批申请」中审批本项目）**将其批准为 `approved`。
  - **属于其他企业租户的项目**：平台严禁跨租户访问，请立即在代码中移除或更正该 `{id}`。
- **验证结果**：当权限申请状态在 **「帮助与支持 > 我的申请」** 中变为 **`approved`**（或已被添加为项目协作者）后，**必须继续使用原调用用户的同一凭据**在 **「沙箱调试台」** 页面或客户端复测 `GET /sandbox/product/v1/projects/{id}` 并观察返回结果（在凭据仍有效且配额可用时将返回 `200 OK`）。

### 4.3 场景三：同时缺少接口 `scope` 与项目资源访问权（`SCOPE_AND_ACCESS_DENIED`）

- **现象**：调用 `GET /sandbox/product/v1/projects/{id}` 返回 HTTP `403`，`error.code` 为 `SCOPE_AND_ACCESS_DENIED`（`credential_has_scope: false`，`user_has_project_access: false`），且调用用户在网页端也打不开该项目 `{id}`。
- **可能原因**：当前使用的 API 凭据既未勾选 `project:read`，同时凭据绑定的调用用户（`member` 或 `guest`）也未获得目标项目 `{id}` 的访问授权。
- **检查方法**：
  - 查看错误响应体中的 `error.details`（确认 `credential_has_scope` 与 `user_has_project_access` 均为 `false`），并在 **「凭据管理」** 与 **「项目中心」** 页面分别核对凭据 `scope` 和项目访问权。
  - **单边修复仍会报错的原因**：如果你只让本空间 `admin` 或该项目负责人批准了项目 `read` 权限，却没有去 **「凭据管理」** 给凭据勾选 `project:read`，再次调用会变为场景一（`INSUFFICIENT_SCOPE`）；反之，如果只勾选了 `project:read` 却未完成项目授权审批，再次调用会变为场景二（`PROJECT_ACCESS_DENIED`），两者都会继续返回 `403`。
- **处理建议**：必须同步完成两步页面修复：
  1. 在 **「开发者与 API 中心 > 凭据管理」** 页面为该凭据勾选 `project:read` 并保存；
  2. 在 **「项目中心 > 申请访问项目」** 页面为调用用户申请目标项目 `{id}` 的 `read` 权限，并由**本工作空间 `admin` 或该项目负责人**审批为 `approved`。
- **验证结果**：两项条件均修复完成后，使用**原调用用户身份及原凭据**在 **「沙箱调试台」** 页面或客户端复测 `GET /sandbox/product/v1/projects/{id}` 并观察结果。

## 5. 调用接口返回 HTTP 429 时，如何区分 `RATE_LIMITED` 与 `QUOTA_EXCEEDED`？

当接口返回 HTTP `429` 时，代表请求触发了协作平台的调用频率或累计配额限制。协作平台对限流窗口、统计维度、累计配额周期与重置规则采用统一的**固定配置**。请根据响应体中的 `error.code` 严格区分 **`RATE_LIMITED`（短时限流）** 与 **`QUOTA_EXCEEDED`（累计额度耗尽）**，切勿对所有 `429` 一律采取“降速重试”或假定“等待一分钟必定恢复”：

| 对比维度 | 短时限流（`RATE_LIMITED`） | 累计额度耗尽（`QUOTA_EXCEEDED`） |
| :--- | :--- | :--- |
| **HTTP 状态码与错误码** | HTTP `429`，`error.code` 为 `RATE_LIMITED` | HTTP `429`，`error.code` 为 `QUOTA_EXCEEDED` |
| **统计维度** | 按**单个 API 凭据（`credential_id`）**独立统计 | 按**所属工作空间（`workspace_id`）**汇总统计全空间所有凭据的有效调用量 |
| **固定限额与统计窗口** | **60 秒（1 分钟）固定时间窗口内最多 60 次请求**（`60 次 / 60 秒`） | **每个自然日（00:00～24:00 UTC+8）累计最多 5,000 次请求**（`5,000 次 / 自然日`） |
| **自动重置规则** | 当前 60 秒固定窗口结束时自动清零计数（响应返回 `retry_after_seconds`，范围 `1`～`60` 秒） | 每日 **00:00（UTC+8）** 自动将工作空间当日已用配额重置为 `0` |
| **等待后重试能否恢复？** | **不保证无条件恢复**（仅当共用该凭据的其他并发任务已停止高频请求，且所属工作空间的当日 5,000 次累计配额尚未耗尽时，等待 `retry_after_seconds` 秒后重试才可恢复） | **当日重置前无法通过等待几分钟恢复**（在次日 `00:00 UTC+8` 自动重置前，降低请求速度或等待几分钟重试仍会持续返回 `QUOTA_EXCEEDED`） |

### 5.1 `RATE_LIMITED`（短时限流）检查与处理步骤
- **检查方法**：
  1. 查看 `429` 响应体中的 `error.code` 是否为 `RATE_LIMITED`，并读取 `error.details.retry_after_seconds`（当前 60 秒窗口剩余秒数）与 `window_limit: 60`。
  2. 前往左侧导航栏 **「开发者与 API 中心 > 调用记录与配额看板」** 页面，检查该 `credential_id` 是否被多个脚本、定时任务或死循环同时高频调用，同时查看看板顶部的 **「工作空间今日剩余配额」** 是否大于 `0`。
- **处理建议**：
  1. 先暂停或限流共用该凭据的其他并发进程，将单凭据调用频率控制在每 60 秒不超过 60 次，并在客户端代码中根据 `retry_after_seconds` 实现退避等待。
  2. 等待当前 60 秒窗口结束后再发起请求。
- **验证结果**：在确认无其他进程争抢同一凭据窗口且工作空间当日配额未耗尽的前提下，等待 `retry_after_seconds` 秒后，使用原凭据在 **「沙箱调试台」** 页面或客户端单次复测接口并观察返回结果。

### 5.2 `QUOTA_EXCEEDED`（累计额度耗尽）检查与处理步骤
- **检查方法**：
  1. 查看 `429` 响应体中的 `error.code` 是否为 `QUOTA_EXCEEDED`，并读取 `error.details.daily_quota_limit: 5000`、`used_today: 5000` 及 `reset_at`（次日 `00:00:00+08:00`）。
  2. 在 **「开发者与 API 中心 > 调用记录与配额看板」** 页面查看本工作空间当日各凭据的调用量排行，定位消耗完 5,000 次日额度的具体凭据。
- **处理建议**：
  1. **立即停止客户端重试循环**，因为在次日 `00:00（UTC+8）` 自动重置前，继续重试只会不断返回 `429 QUOTA_EXCEEDED`。
  2. 若业务允许等待，待次日 `00:00（UTC+8）` 配额自动清零后再恢复调用，并优化异常高频脚本。
  3. 若核心业务受阻需要反馈，可先在 **Ordo 智能支持中心** 整理包含 `request_id`、工作空间 ID 与受阻情况的反馈材料，再前往顶部导航栏 **「帮助与支持 > 我的工单 > + 提交工单」** 页面自行提交支持工单（注意：Ordo 助手本身不能重置或扩容配额，且提交工单不代表配额会立即恢复）。
- **验证结果**：待次日 `00:00（UTC+8）` 自动重置（或工单经后台处理完毕）后，使用原调用凭据在 **「沙箱调试台」** 页面复测接口并观察结果。

## 6. 示例：从“双缺 403”到“429 配额耗尽”的页面自查与排错过程

> **示例说明（以下为假设情境，仅供演示排错方法，非当前用户真实状态）**：  
> **前提设定**：假设在“天枢科技（`ws_ts_01`）”工作空间中，数据分析师小郑（角色为 `member`）使用凭据 `cred_zheng_01` 调用 `GET /sandbox/product/v1/projects/proj_bi_2026` 同步私有报表项目数据，先后遇到 `403` 与 `429` 报错。

1. **第一阶段：排查 `403`（区分单边修复与双边修复）**：
   - 小郑首次调用返回 `403`，响应体中 `error.code` 为 `SCOPE_AND_ACCESS_DENIED`，`credential_has_scope: false` 且 `user_has_project_access: false`。小郑将该脱敏响应发给 Ordo 询问，助手指出该错误属于“同时缺少凭据 `project:read` 与项目访问权限”。
   - 小郑先联系该项目负责人将自己加入私有项目 `proj_bi_2026`（授予 `read` 权限），随后立即重跑脚本，结果仍然返回 `403`，但错误码变为 `INSUFFICIENT_SCOPE`。
   - 小郑意识到只修了项目权限、漏修了凭据 `scope`，于是前往 **「开发者与 API 中心 > 凭据管理」** 页面为 `cred_zheng_01` 勾选 `project:read`，再用小郑本人的 `cred_zheng_01` 在 **「沙箱调试台」** 页面复测，观察到返回 `200 OK`。
2. **第二阶段：排查 `429`（区分 `RATE_LIMITED` 与 `QUOTA_EXCEEDED`）**：
   - 当晚小郑启动全量拉取脚本后收到 `429` 报错。小郑暂停脚本等待了数分钟后单次重试，发现依然返回 `429`。
   - 小郑查看响应体中的 `error.code`，并在 **「开发者与 API 中心 > 调用记录与配额看板」** 页面核对，发现报错标识为 `QUOTA_EXCEEDED`（工作空间当日 5,000 次累计额度已被团队另一个高频轮询脚本耗尽），而非单凭据 60 次/60 秒的短时限流 `RATE_LIMITED`。因此单纯等待几分钟无法恢复。小郑随即关闭异常轮询脚本，并在次日 `00:00（UTC+8）` 配额自动重置后用原凭据复测恢复正常。

## 7. 常见问题（FAQ）

### 问：我在「沙箱调试台」页面里测试接口已经返回 `200 OK`（带 `sandbox` 标识），为什么我们公司的外部服务器脚本调用还是报 `401` 或 `403`？
答：“沙箱验证通过”仅证明你在页面上所选的测试凭据（`test_credential_id`）、绑定的用户权限与请求参数在协作平台受控沙箱中是正确的，不自动代表你外部生产或测试服务器上的代码问题已解决。请重点核查外部服务器：（1）环境变量里的 `Authorization` Token 是否仍缓存着旧的已吊销凭据；（2）外部脚本实际使用的是否是另一个未获授权账号的凭据；（3）外部脚本拼接的 `{id}` 参数是否带有大写字母、换行符或编码错误。

### 问：排查员工账号的 API `403` 报错时，能不能直接把管理员（`admin`）的 API 凭据配到该员工的脚本里跑通？
答：不能。首先，平台安全规范要求修复权限后**必须使用原调用用户身份及对应凭据复测**，将 `admin` 凭据交由普通脚本使用会导致该脚本拥有全工作空间所有私有项目的读取权限，违反最小权限原则；其次，即便使用 `admin` 的凭据，如果该凭据本身未勾选 `project:read`，同样会触发 `403 INSUFFICIENT_SCOPE`。正确做法是在页面上为原调用账号补齐所需的项目 `read` 权限与凭据 `project:read` 后，用原凭据复测并观察结果。
